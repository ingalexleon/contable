# PostgreSQL migration and frontend-backend alignment (v2)

This change set (from initial commit dfb2d46 to HEAD) completes a full-stack accounting management system: async PostgreSQL support via `asyncpg`, SQLite defaults for local development, SQL-level aggregation in dashboard/reports, extended Excel exports, endpoint path alignment between frontend and backend, and an Alembic migration with proper unique constraints. Five issues from the v1 review have been addressed — credentials removed, aggregation moved to SQL, unique constraint added, unused import cleaned up.

**Watch for:** Monthly revenue chart still loads individual payment rows into Python for grouping (confirmed). The `create_client_service` endpoint will surface a raw `IntegrityError` on duplicate assignment since no application-level handling wraps the new unique constraint (confirmed). The `monthly_revenue` field on the dashboard sums *all-time* paid amounts, not the current month (likely naming confusion, not a bug per se).

**Verdict**: APPROVED

## High-level view

Credential and Alembic driver concerns from v1 are resolved — `config.py` defaults to SQLite, `alembic.ini` carries a placeholder, and the custom async `env.py` runner makes `asyncpg` in the ini intentional.

The dashboard and general report endpoints now use SQL aggregation for KPI counts and sums. One residual pattern remains: the monthly revenue chart fetches all paid payment rows and groups them in Python. For a small firm this is negligible, but it's the last unbounded fetch in the reports module.

The unique constraint on `client_services(client_id, service_id)` is present in both the model and migration. The assignment endpoint does not catch `IntegrityError`, so a duplicate will return a 500 rather than a descriptive 409.

## Monthly revenue chart: last unbounded fetch

The chart data path still fetches individual rows after the v1 fix moved main KPIs to SQL:

```python
monthly_chart_result = await db.execute(
    select(Payment.payment_date, Payment.amount).where(
        Payment.status == PaymentStatus.PAID,
        Payment.payment_date.isnot(None),
    )
)
monthly_data = defaultdict(float)
for row in monthly_chart_result.all():
    payment_date, amount = row
    if payment_date:
        key = f"{month_names[payment_date.month]} {payment_date.year}"
        monthly_data[key] += amount
```

This loads N rows where N = all paid payments with a date. A SQL `GROUP BY EXTRACT(year FROM payment_date), EXTRACT(month FROM payment_date)` would return at most 12*Y rows regardless of payment volume, avoiding transmitting individual amounts over the DB connection.

The practical difficulty: SQLite (used in tests) doesn't support `EXTRACT`. A pragmatic fix is filtering to the last 12 months (`WHERE payment_date >= now - 12 months`) which bounds the result set regardless of dialect.

## Duplicate assignment surfaces raw 500

```python
@router.post("/assign", response_model=ClientServiceResponse)
async def create_client_service(data: ClientServiceCreate, ...):
    cs = ClientService(**data.model_dump())
    db.add(cs)
    await db.flush()
```

With `UniqueConstraint("client_id", "service_id", name="uq_client_service")` now in place, attempting to assign the same service twice raises `sqlalchemy.exc.IntegrityError`. The `get_db` dependency rolls back but the exception propagates to FastAPI's default 500 handler. A `try/except IntegrityError` returning `HTTPException(status_code=409, detail="Service already assigned to this client")` would give the frontend something actionable.
