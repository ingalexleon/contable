# PostgreSQL migration and frontend-backend contract alignment

This change migrates the backend's default database target from SQLite to a Railway-hosted PostgreSQL instance, fixes endpoint path mismatches between the React frontend and the FastAPI backend, and extends the reports/export surface to fulfill the dashboard's data contract. The approach is pragmatic: hardcode the Railway connection string as the default, reshape report endpoints to emit the flat fields the frontend already expects, and add service/all-data Excel export paths that were missing. An Alembic migration codifies the full schema for PostgreSQL deployments.

**Watch for:** Hardcoded production database credentials in source-controlled files (confirmed). The Alembic config uses the async driver (`asyncpg`) which will fail with standard Alembic runners (confirmed). Dashboard aggregation loads all payments into memory regardless of dataset size (confirmed).

## High-level view

The credential situation is the gating concern. The Railway PostgreSQL password appears verbatim in `config.py`, `alembic.ini`, and `.env.example` — three source-controlled files. Anyone with repo access has full database credentials, and rotating the password requires a code change.

The Alembic migration file is structurally correct but the `alembic.ini` driver string (`postgresql+asyncpg://`) is incompatible with Alembic's synchronous migration runner. Migrations will fail unless invoked through a custom async wrapper or the driver is changed to `psycopg2`.

The dashboard endpoint materializes all payments in Python to compute aggregates — fine for a small firm, but will degrade linearly with payment volume since there's no date-range filtering or database-level aggregation.

The `client_services` table lacks a uniqueness constraint on `(client_id, service_id)`, allowing duplicate assignments with no detection at the database level.

## Credentials committed to source control

The Railway PostgreSQL connection string — including the password `XCjmTvSLwAxNkCJfjGEsYEMZeBddjOpL` — is hardcoded in three places: `backend/app/core/config.py` (as the default for `DATABASE_URL`), `backend/alembic.ini` (the `sqlalchemy.url` value), and `.env.example`. These files are tracked in git. The `config.py` pattern of providing a default value means the application will connect to production even when no `.env` file is present — a developer running tests without a `.env` could inadvertently write to the production database.

The fix: remove the default from `DATABASE_URL` in `config.py` (or default to the SQLite path for local dev), use a placeholder in `.env.example`, and configure `alembic.ini` to read the URL from an environment variable via `env.py` (which the Alembic scaffold already supports with `config.set_main_option`).

## Alembic async driver incompatibility

`alembic.ini` sets `sqlalchemy.url = postgresql+asyncpg://...`. Alembic's migration runners use synchronous SQLAlchemy by default. Running `alembic upgrade head` with this URL will raise an error because `asyncpg` is an async-only driver. The project's `alembic/env.py` may have a custom async runner, but if it uses the stock template, migrations will not execute. The migration file itself (`001_initial_schema.py`) uses synchronous `op.*` calls so the DDL is fine — only the connection URL is problematic.

## Dashboard in-memory aggregation

The `/reports/dashboard` endpoint loads every payment row into Python:

```python
payments_result = await db.execute(select(Payment))
payments = payments_result.scalars().all()
monthly_revenue = sum(p.amount for p in payments if p.status == PaymentStatus.PAID)
```

This is O(n) memory and CPU that grows with the payment table. The monthly revenue chart iterates the same list a second time. Moving to `SELECT SUM(amount), EXTRACT(month FROM payment_date) ... GROUP BY` would keep memory constant. The same pattern appears in `/reports/general`.

## Missing unique constraint on client-service

The `client_services` migration creates no unique constraint on `(client_id, service_id)`. The application code in `services.py` does not check for existing assignments before inserting. A client can be assigned the same service multiple times at different prices with no mechanism to determine which is canonical. A unique index (possibly partial, scoped to `is_active = True`) would prevent this.
