# Full-stack accounting office management system

A greenfield web application for a Mexican accounting office ("despacho contable"), implementing client management, service catalog with custom pricing, payment tracking with file-upload proofs, role-based access control, audit logging, and Excel reporting. The backend is FastAPI with SQLAlchemy (async), JWT auth, and bcrypt password hashing. The frontend is React 18 with TypeScript, Vite, Tailwind CSS, shadcn/ui components, and TanStack Query. Docker Compose ties it together with PostgreSQL and nginx reverse proxy.

**Watch for:** Frontend login is broken due to a content-type mismatch with the backend (confirmed). The frontend admin-role check reads a field (`role`) that the backend never sends, making RBAC enforcement invisible on the client (confirmed). No rate limiting on authentication endpoints (confirmed). Password reset tokens are replayable until expiry (confirmed). The `SECRET_KEY` default is a well-known string shipped in code (confirmed).

## High-level view

The authentication flow has two integration bugs that prevent the system from working as deployed. The frontend sends login credentials as form-encoded data with a `username` field, but the backend expects a JSON body with an `email` field. Independently, the `/auth/me` response returns `role_name` (e.g., "Administrador") but the frontend `User` type expects a `role` field, so the admin check `user?.role === 'administrador'` will never match — every user appears as non-admin in the UI.

The RBAC model is role-name-string-based: the backend hardcodes `"Administrador"` in `require_admin`. The `permissions` JSON column on the Role model is never consulted at runtime, making the permission grants dead data.

Security posture is missing several layers expected for a financial application: no rate limiting on login or password reset, no token revocation or blacklisting (neither for access tokens nor reset tokens), and the default `SECRET_KEY` is a static string embedded in source. There is no authenticated download endpoint for uploaded proofs — files are stored on disk without a serving mechanism, and the `file_path` is leaked verbatim in the API response.

The frontend-backend contract for client types is misaligned: the backend enum values are Spanish-titled strings ("Persona Fisica"), while the frontend sends lowercase-underscore values ("persona_fisica"). The frontend also sends `tax_id` where the backend expects `rfc`. Both mismatches cause silent data loss or 422 errors in production.

1. **Login content-type mismatch** — Frontend sends `application/x-www-form-urlencoded` with `username` field; backend expects JSON with `email` field. Login is non-functional as deployed. Fix the frontend to send JSON `{email, password}`.
2. **Admin role detection broken on frontend** — `auth-context.tsx` reads `user?.role` but the backend returns `role_name`. Map `role_name` to `role` in the frontend type or fix the property access.
3. **Client type enum mismatch** — Frontend sends `persona_fisica`; backend expects `"Persona Fisica"`. Either align the enum values or add a mapping layer.
4. **Hardcoded SECRET_KEY default** — `dev-secret-key-change-in-production` ships in `config.py` and `docker-compose.yml`. If no env var is set, production signs tokens with a public string. Fail startup if SECRET_KEY matches the default in non-debug mode.
5. **No rate limiting on auth endpoints** — Login and password reset have no throttle, enabling brute-force attacks. Add rate limiting (e.g., `slowapi`).
6. **Reset tokens are replayable** — No server-side invalidation after use. A leaked reset link can reset the password multiple times within the 30-minute window. Store used tokens or increment a password-change counter in the JWT claim.
7. **File upload path exposed in API** — `PaymentProofResponse.file_path` leaks the server filesystem path. Return a download URL or opaque identifier instead.
8. **No file download endpoint** — Uploaded proofs are stored on disk but there's no route to serve them. Add an authenticated file-serve endpoint.
9. **Inactivity timeout only on frontend** — The 30-minute session timeout in `auth-context.tsx` is purely client-side. A stolen token remains valid for 8 hours (ACCESS_TOKEN_EXPIRE_MINUTES=480) regardless of activity.
10. **Payment amount accepts negative values** — The `PaymentCreate` schema uses bare `float` with no `gt=0` constraint. Add `Field(gt=0)` to prevent negative or zero payments.

## Login and auth-context integration failures

The frontend `login` function in `auth-context.tsx` constructs a `URLSearchParams` body with fields `username` and `password`, then posts with `Content-Type: application/x-www-form-urlencoded`:

```typescript
const formData = new URLSearchParams()
formData.append('username', email)
formData.append('password', password)
const res = await api.post('/auth/login', formData, {
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
})
```

The backend `LoginRequest` is a Pydantic BaseModel expecting a JSON body with `email` and `password`. FastAPI will reject the form-encoded request with a 422 validation error. Even if the content type were fixed, the field name mismatch (`username` vs `email`) would still fail validation.

After login, the frontend fetches `/auth/me` and stores the response as a `User`. The backend `UserResponse` schema has a `role_name` field (containing "Administrador" or "Usuario Estandar"), but the frontend `User` type defines `role: string`. The auth context checks:

```typescript
const isAdmin = user?.role === 'admin' || user?.role === 'administrador'
```

Since the API response field is `role_name` (not `role`), `user?.role` will be `undefined`. No user will ever appear as admin in the frontend, hiding all admin-only UI elements for all users.

## Secret management and token security

The `SECRET_KEY` in `config.py` defaults to `"dev-secret-key-change-in-production"` and `docker-compose.yml` repeats it as a fallback. If an operator deploys without setting the environment variable, all JWT tokens are signed with a publicly-known key, enabling trivial token forgery.

Access tokens have an 8-hour lifetime with no server-side revocation. The `/auth/logout` endpoint is a no-op — the token remains valid until expiry. A leaked token grants full access for its entire lifetime.

Password reset tokens share the same signing key, differentiated only by a `"type": "reset"` claim. After a successful reset, the token is not invalidated: the same token can replay the password reset within the 30-minute window. An attacker who intercepts the reset email can repeatedly reset the password even after the legitimate user has already used the link.

## RBAC enforcement gap

The `permissions` JSON column on the `Role` model is populated during seeding (`{"all": True}` and `{"read": True, "reports": True}`) but never read by any authorization logic — it's dead data. Adding new roles or granular permissions requires code changes.

There is no per-entity access scoping: any authenticated user sees the entire dataset. A standard user can view all clients, all payments, all services, and export all data via the Excel endpoint.

## Client-type and field name mismatch

The backend `ClientType` enum defines values as Spanish-titled strings: `"Persona Fisica"`, `"Persona Moral"`, `"Regimen Simplificado"`. The frontend form sends lowercase underscore variants (`persona_fisica`, `persona_moral`, `regimen_simplificado`). Pydantic will reject these with a 422. The backend tests pass only because they use the Spanish-titled values directly.

The frontend `Client` type defines `tax_id` where the backend schema expects `rfc`. The `ClientForm` registers a `tax_id` field, so client creation from the frontend sends the RFC value under the wrong key — clients are created without their tax identifier.

## File upload memory exhaustion and missing download

The upload endpoint calls `file.read()` to load the entire file into memory before checking `len(content) > settings.MAX_UPLOAD_SIZE`. A malicious upload larger than available RAM would exhaust server memory before the size check triggers. Reading in chunks or checking `Content-Length` headers first would be safer.

The `PaymentProofResponse` returns `file_path` as a raw server path (e.g., `uploads/abc123.pdf`). There is no route to serve these files, so the frontend cannot display proof documents. The exposed path also leaks directory structure. The system needs an authenticated download endpoint that streams the file through an authorization check.

## Audit logging gaps

The `ip_address` field is always `None` because no caller passes the request IP to `log_audit`. For a financial system's audit trail, capturing the originating IP is important for forensic purposes.

Login attempts (successful and failed) are not audit-logged. Authentication events are typically the most critical audit records for financial applications.

## Test coverage gaps

Not tested: service catalog endpoints, client-service assignments, payment deletion, Excel export streaming, file size rejection, invalid file type rejection, the effect of soft-deleted entities on reports, or frontend integration. There are no frontend tests.
