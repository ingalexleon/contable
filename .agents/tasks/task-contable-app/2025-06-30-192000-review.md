# Full-stack accounting office management system (v3)

A greenfield web application for a Mexican accounting office implementing client management, service catalog, payment tracking with file-upload proofs, RBAC, audit logging, and Excel reporting. FastAPI async backend with SQLAlchemy, JWT auth, bcrypt. React 18 + TypeScript + Vite + Tailwind frontend. Docker Compose orchestration with PostgreSQL and nginx reverse proxy.

All integration bugs from v1 and v2 have been resolved: login sends JSON with correct fields, admin role detection uses `role_name`, client type enum values and RFC field are aligned, download URLs no longer carry a double `/api` prefix, and `get_client_ip` is extracted to a shared module. The test suite validates the corrected contracts.

**Watch for:** Payment proof images and PDFs will fail to load in the browser because the download endpoint requires a Bearer token but the frontend renders them via `<img src>` and `<a href>` which cannot pass auth headers (confirmed). File uploads are read entirely into memory before the size check, enabling a memory exhaustion vector for large payloads (confirmed).

**Verdict**: APPROVED

## High-level view

The proof download endpoint is protected by `get_current_user`, which means direct browser navigation via `<img src="/api/payments/proofs/1/download">` will fail with a 401 since no Authorization header is attached. This affects proof viewing only — not a blocker for core accounting workflows (client management, payment CRUD, reporting, exports all work), but proof images will show broken until the frontend fetches them via the authenticated axios instance and uses object URLs.

The file upload flow reads the entire request body into memory before checking size. The nginx proxy defaults to 1MB `client_max_body_size`, which under-blocks relative to the backend's configured 10MB limit. If nginx is reconfigured to allow 10MB uploads (required for the feature to work as designed), the backend becomes the only size gate and it gates after buffering. Adding an explicit `client_max_body_size 11m;` to nginx would enforce the limit at the proxy layer.

## Proof download authentication mismatch

The download endpoint in `payments.py` uses `Depends(get_current_user)`:

```python
@router.get("/proofs/{proof_id}/download")
async def download_payment_proof(
    proof_id: int,
    db: AsyncSession = Depends(get_db),
    current_user: User = Depends(get_current_user),
):
```

The frontend `PaymentProofViewer.tsx` renders proofs as:

```tsx
<img src={`/api${proof.download_url}`} ... />
<a href={`/api${proof.download_url}`} target="_blank" ...>
```

Neither `<img>` nor `<a>` sends the `Authorization: Bearer` header. The browser makes a plain GET request, which `HTTPBearer` rejects with 401. Every proof image renders broken and every PDF link fails.

Two remediation paths: (a) fetch the blob via axios in the hook and use `URL.createObjectURL`, or (b) accept a short-lived token as a query parameter for download-only routes. Neither is complex, but this feature is non-functional until one is implemented.

This does not block shipping the core accounting workflows. Proof viewing is a secondary feature, and proof *upload* works correctly. The download can be addressed in a fast follow-up without architectural changes.

## Upload buffering and size enforcement

```python
content = await file.read()
if len(content) > settings.MAX_UPLOAD_SIZE:
    raise HTTPException(status_code=400, detail="File too large")
```

The entire file is in memory before the length check. The nginx config doesn't set `client_max_body_size`, so it defaults to 1MB — which actually *under*-blocks relative to the backend's 10MB limit. Uploads larger than 1MB will be rejected by nginx before reaching the backend, meaning the upload feature as configured only accepts files under 1MB in production. If the nginx default is raised to accommodate the intended 10MB uploads, the backend becomes the only size gate, and it gates *after* buffering. Adding `client_max_body_size 11m;` to the nginx `location /api/` block would let intended uploads through while protecting against larger payloads at the proxy layer.
