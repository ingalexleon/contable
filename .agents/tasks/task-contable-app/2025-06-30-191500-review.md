# Full-stack accounting office management system (v2)

A greenfield web application for a Mexican accounting office ("despacho contable") providing client management, service catalog, payment tracking with file-upload proofs, RBAC, audit logging, and Excel reporting. The backend is FastAPI with async SQLAlchemy, JWT auth, and bcrypt. The frontend is React 18 with TypeScript, Vite, Tailwind CSS, and shadcn/ui. Docker Compose orchestrates PostgreSQL, the backend, and an nginx-served frontend.

The v1 integration bugs (login content-type mismatch, admin role detection, client type/RFC field misalignment, missing download endpoint, exposed file paths, missing payment amount validation, and absent IP logging) have all been addressed. The test suite (26 tests) passes clean.

**Watch for:** Payment proof downloads will 404 in the deployed Docker environment due to a double `/api` prefix in the frontend URL construction (confirmed). The `_get_client_ip` helper is copy-pasted across three router modules — a minor maintenance concern (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The v1 critical integration blockers are resolved: login sends JSON with the correct field names, admin detection reads `role_name` case-insensitively, and client form enum values and RFC field are aligned with the backend schema.

The new file download endpoint is gated behind `get_current_user` and serves files via `FileResponse`. However, the backend hardcodes the full path including the `/api` prefix in `download_url`, while the frontend's `PaymentProofViewer` prepends its own `/api` prefix when constructing `<img src>` and `<a href>` attributes. This produces `/api/api/payments/proofs/{id}/download`, which will not resolve through nginx.

Audit logging now captures client IP via `_get_client_ip(request)` across all mutation endpoints, correctly parsing `X-Forwarded-For` for the nginx reverse-proxy stack. The helper is duplicated identically in three files; extracting it would reduce drift risk.

## Proof download URL double-prefix

The `_build_proof_response` helper in `payments.py` constructs:

```python
"download_url": f"/api/payments/proofs/{proof.id}/download",
```

This path already includes the `/api` prefix that results from the router being mounted with `app.include_router(payments.router, prefix="/api")`. The frontend `PaymentProofViewer.tsx` then builds direct browser URLs:

```tsx
src={`/api${proof.download_url}`}
href={`/api${proof.download_url}`}
```

The resulting path `/api/api/payments/proofs/{id}/download` doesn't match any nginx location or backend route. Images won't render and PDF links will 404. The test in `test_payments.py` asserts `f"/api/payments/proofs/{data['id']}/download" == data["download_url"]` — it validates the backend response format but doesn't exercise the frontend consumption path.

The simplest fix: change `_build_proof_response` to return `/payments/proofs/{proof.id}/download` (without the `/api` prefix), since the frontend already knows to prepend `/api` for all backend requests.

## IP extraction duplication

`_get_client_ip` appears identically in three router files. If the IP extraction logic needs to change (e.g., to handle `X-Real-IP` or to validate against a trusted proxy list), all three copies must be updated in lockstep. Moving it next to `log_audit` in `middleware/audit.py` — or making it a FastAPI dependency — would centralize the logic.
