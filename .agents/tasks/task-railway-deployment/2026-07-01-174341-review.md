# Railway deployment split for backend and frontend services

The change adapts a FastAPI + React app for Railway's separate-service deployment model. The backend gains a configurable `PORT` env var and a CORS regex for `*.up.railway.app`. The frontend's axios `baseURL` becomes configurable via `VITE_API_URL` (build-time), and a new `nginx.railway.conf` serves the SPA without proxying API calls. Both services get `railway.json` files, and the existing `docker-compose.yml` preserves the local-dev proxy behavior by passing `NGINX_CONF=nginx.conf` as a build arg.

**Watch for:** The frontend nginx config listens on port 80, but Railway injects a dynamic `PORT` env var and expects the service to bind to it — this will cause deployment failures (confirmed). The `VITE_API_URL` must include the `/api` path prefix at deploy time or all frontend requests will hit the wrong path (confirmed). The backend `railway.json` `startCommand` duplicates the Dockerfile CMD, creating a maintenance divergence (confirmed).

## High-level view

The backend adds `PORT` from the environment, uses shell-form CMD for variable expansion, and opens CORS to Railway subdomains via `allow_origin_regex`. The `railway.json` healthcheck points at `/api/health`, which exists.

The frontend swaps nginx configs via a build arg (`NGINX_CONF`). However, the Railway nginx config hardcodes `listen 80` instead of reading from Railway's `PORT` env var. Railway does not expose port 80 to services; it assigns a random port via `$PORT`. Nginx must listen on `$PORT` for the container to receive traffic.

The `VITE_API_URL` env var is baked at build time, which is correct for Vite. But the value the deployer sets must include the `/api` path segment (e.g., `https://backend-xyz.up.railway.app/api`), because the frontend code uses it as the full baseURL. This isn't documented or enforced anywhere and is easy to get wrong (setting just the origin would break every API call).

## Railway PORT contract for the frontend

Railway requires every service to bind to the port specified by the `PORT` environment variable. The `nginx.railway.conf` has:

```nginx
listen 80;
```

Nginx will listen on port 80 inside the container, but Railway routes traffic to whatever `$PORT` it assigned (typically 3000-9000 range). The container will appear healthy to docker but unreachable to Railway's router.

The standard fix for nginx on Railway is to use `envsubst` to template the port at container startup:

```dockerfile
CMD ["/bin/sh", "-c", "envsubst '$$PORT' < /etc/nginx/conf.d/default.conf.template > /etc/nginx/conf.d/default.conf && nginx -g 'daemon off;'"]
```

With `listen ${PORT};` in the template file. This is a blocking deployment issue.

## VITE_API_URL path semantics

The frontend axios client sets:

```typescript
baseURL: import.meta.env.VITE_API_URL || '/api'
```

All backend routes are prefixed with `/api` (visible in `main.py` where every router uses `prefix="/api"`). On Railway, `VITE_API_URL` must be set to something like `https://contable-backend-production.up.railway.app/api` — the full base path including `/api`.

If someone sets `VITE_API_URL=https://contable-backend-production.up.railway.app` (the natural first instinct), the client will request `https://contable-backend-production.up.railway.app/auth/login` instead of `.../api/auth/login`, resulting in 404s across the board. Either document the expected format or make the code defensive:

```typescript
baseURL: import.meta.env.VITE_API_URL ? `${import.meta.env.VITE_API_URL}/api` : '/api'
```

## Backend start command duplication

The backend Dockerfile CMD and `railway.json` `startCommand` both specify:

```
uvicorn app.main:app --host 0.0.0.0 --port $PORT
```

Railway's `startCommand` takes precedence over the Dockerfile CMD when deployed, making the Dockerfile CMD relevant only for local `docker-compose` use. Changes to startup flags (adding `--workers`, `--timeout-keep-alive`, etc.) need to be made in two places. The cleaner pattern is to omit `startCommand` from `railway.json` and let the Dockerfile CMD be the single source of truth.

## CORS surface area

The `allow_origin_regex=r"https://.*\.up\.railway\.app"` pattern matches any subdomain under `up.railway.app`. Any application deployed on Railway by any user could make authenticated cross-origin requests to this backend if they know the URL. For an accounting application, tighten to the specific frontend domain once known:

```python
allow_origin_regex=r"https://contable-frontend.*\.up\.railway\.app"
```

Or set the exact origin via an environment variable and drop the regex in production.
